# Hermes DLC — спецификация

Версия 0.2 · статус: черновик на согласование
Целевая платформа: Hermes Agent (NousResearch), Hermes Desktop / Webapp.
Основание: исходники `NousResearch/hermes-agent` и `plastic-labs/honcho` по состоянию на ноябрь 2026.

---

## 0. Назначение

DLC — пакет-дополнение к Hermes Agent. Он превращает Hermes из одиночного агента в систему,
которая:

1. **Понимает задачу до исполнения**: оценивает сложность, формулирует критерий готовности,
   раскладывает задачу на подзадачи по требуемым компетенциям.
2. **Подбирает исполнителя под компетенцию**, а не под типовую роль. Узкая задача — узкий
   специалист. Простая — простой агент.
3. **Ведёт работу на Kanban**: подзадачи, зависимости, ревью, история.
4. **Учится на каждой задаче**: после выполнения разбирает результат, извлекает уроки и
   улучшает конкретного агента. Библиотека агентов растёт и становится точнее.
5. **Помнит пользователя** (Honcho на локальных эмбеддингах) и **знает проект** (локальный RAG).

### 0.1 Ограничения, заданные пользователем

- **Никакой автоматической установки.** Ни скриптов, ни команд, которые меняют систему
  без участия пользователя. Установка, включение и настройка — через графический интерфейс.
- Основной интерфейс пользователя — **Hermes Desktop**. Терминал не должен требоваться
  для повседневной работы. Где без него не обойтись (сервер Honcho), это помечено явно.
- Пакет **не изменяет ядро Hermes**: только публичный API плагинов, хуки, скиллы,
  профили, desktop-SDK.

### 0.2 Термины

| Термин | Значение |
|---|---|
| Оркестратор | Агент, с которым пользователь общается в чате (обычно профиль `default`). Планирует, подбирает агентов, проводит ретроспективы. |
| Агент-специалист | Профиль Hermes со своим SOUL, моделью и навыками, зарегистрированный в библиотеке DLC. |
| Библиотека агентов | Реестр специалистов: компетенция, домены, уровень, статистика, уроки, версии SOUL. |
| SOUL | `SOUL.md` профиля — идентичность и методика агента, первый слот системного промпта. |
| Компетенция | Что конкретно нужно уметь для подзадачи: область, стек, тип артефакта, стандарты качества. |
| DoD | Definition of Done — проверяемый критерий готовности. |
| Урок | Конкретное проверяемое правило, извлечённое из выполненной задачи. |
| Прогон | Одно выполнение Kanban-задачи агентом-специалистом. |

## 1. Что уже есть в Hermes и что добавляет DLC

| Возможность | Hermes (и где в GUI) | DLC добавляет |
|---|---|---|
| Kanban | Доска на SQLite, диспетчер в gateway, исполнитель задачи = профиль. GUI: страница **Kanban** в Desktop (переключатель досок, диалог создания задачи с полями assignee, skills, workspace). Хуки `kanban_task_completed/blocked/claimed`. | Протокол планирования; автоучёт прогонов; значки агента и версии на карточках. |
| Профили | Изолированный `HERMES_HOME`: config, SOUL, skills, memory. GUI: **Profiles** — создание, клонирование, редактирование модели, описания и SOUL. | Библиотека поверх профилей: поиск по компетенции, статистика, уроки, версии SOUL, вывод из ротации. |
| Субагенты | `delegate_task`: дети наследуют тулсеты родителя, свой системный промпт задать нельзя. GUI: рамка **Subagents** в чате. | Не используется для специалистов: специалисту нужен свой SOUL, поэтому только Kanban и профили. Субагенты остаются для простых параллельных задач без специализации. |
| Навыки | `~/.hermes/skills`, `skill_manage`, curator. GUI: **Skills**. | Три методических навыка: планирование, создание агента, ретроспектива. |
| Память | `memory.provider` (Honcho и др.) плюс встроенные MEMORY.md/USER.md. GUI: **System → Memory**, **Memory Graph**. | Требования к self-hosted Honcho на локальных эмбеддингах. |
| База знаний | Отдельной подсистемы нет. | Локальный RAG: коллекции, индексация, семантический поиск. |
| Плагины | Пакет = `plugin.yaml` (агентская часть) + `desktop/plugin.js` (часть Desktop) + `dashboard/plugin_api.py` (backend). GUI: **Capabilities → Plugins → Install**, переключатели Agent/Desktop, **Install here** для других профилей, **Settings → Plugins** для настроек. | Всё DLC поставляется одним таким пакетом. |

## 2. Функциональные требования

Приоритет: **M** — обязательно в v1, **S** — желательно в v1, **C** — позже.

### 2.1 Планирование (PLN)

| ID | Требование | Пр. |
|---|---|---|
| PLN-1 | Перед исполнением любой нетривиальной задачи оркестратор формулирует: цель, ожидаемые артефакты, DoD, ограничения, неизвестные и допущения. | M |
| PLN-2 | Если неизвестное меняет план, оркестратор задаёт вопрос пользователю (`clarify`) до декомпозиции. | M |
| PLN-3 | Сложность задачи определяется по шкале `trivial / simple / moderate / complex / novel` (§5.1). Решающая — самая трудная подзадача, а не средняя. | M |
| PLN-4 | `trivial` и `simple` оркестратор выполняет сам, без Kanban. | M |
| PLN-5 | `moderate` и выше разбиваются на подзадачи **по компетенциям и артефактам**. Разбиение по типовым ролям («кодер», «ревьюер», «дизайнер») запрещено. | M |
| PLN-6 | У каждой подзадачи: один исполнитель, входы (родительские задачи), DoD, ограничения, ссылки на нужные RAG-коллекции. | M |
| PLN-7 | Для `complex` и `novel` план показывается пользователю на утверждение до создания задач, если пользователь не разрешил иное (настройка `plan_approval`). | M |
| PLN-8 | Для `novel` первая подзадача — исследование (spike). Основной план строится по его результату. | S |
| PLN-9 | Где нужен ревью, указывается **компетенция ревьюера**. Ревьюер подбирается из библиотеки так же, как исполнитель. | S |

### 2.2 Библиотека агентов (LIB)

| ID | Требование | Пр. |
|---|---|---|
| LIB-1 | Запись агента: `slug`, название, компетенция (1–3 предложения), домены, уровень (`simple / specialist / expert`), имя профиля, модель, статус (`active / retired / proposed`), версия, родитель, эмбеддинг компетенции. | M |
| LIB-2 | Агент = профиль Hermes `ag-<slug>`. Его описание (`--description`) заполняется компетенцией, чтобы встроенный Kanban-декомпозер маршрутизировал задачи. | M |
| LIB-3 | Поиск по **требуемой компетенции** (не по тексту задачи) возвращает кандидатов с оценкой сходства, статистикой и рекомендацией `reuse / adapt / forge` (§5.2). | M |
| LIB-4 | `forge` создаёт нового специалиста по шаблону SOUL (§5.3). SOUL без зоны ответственности, метода, стандартов качества, анти-паттернов и DoD не принимается. | M |
| LIB-5 | `adapt` создаёт узкого наследника существующего агента (`parent_slug`) на основе его SOUL. | M |
| LIB-6 | Режим одобрения (`forge_approval`): `ask` (по умолчанию) — новый агент создаётся в статусе `proposed`, профиль не создаётся, пока пользователь не нажмёт «Одобрить» в GUI; `auto` — сразу. | M |
| LIB-7 | Уровень определяет модель по умолчанию: `simple` — дешёвая, `specialist` — основная, `expert` — сильная, с обязательным ревью. Модели задаются в настройках. | M |
| LIB-8 | Специалист не плодится для `simple`-подзадач. Критерий: специалист нужен, если общий агент с заметной вероятностью (ориентир >20%) сделает неверно или неидиоматично. | M |
| LIB-9 | Библиотека общая для всех профилей и хранится в корне Hermes, а не в данных активного профиля: исполнители Kanban работают в своих `HERMES_HOME`. | M |
| LIB-10 | Обнаружение дублей: при сходстве компетенций двух активных агентов выше `merge_threshold` (0.90) оркестратор предлагает слияние. | S |
| LIB-11 | Экспорт и импорт библиотеки целиком (реестр, SOUL всех версий) для переноса между машинами. | C |

### 2.3 Kanban (KAN)

| ID | Требование | Пр. |
|---|---|---|
| KAN-1 | Подзадачи создаются встроенными `kanban_create` с `assignee = ag-<slug>` и связями через `parents`. Собственной доски DLC не вводит. | M |
| KAN-2 | Тело задачи содержит по шаблону: цель, входы, DoD, ограничения, RAG-коллекции. | M |
| KAN-3 | Профиль каждого агента-специалиста получает тулсет `kanban` и включённый плагин DLC. | M |
| KAN-4 | Исполнитель работает только в своей компетенции. Задачу вне зоны он блокирует (`kanban_block`) и в причине точно описывает нужную компетенцию. | M |
| KAN-5 | Перед `kanban_complete` исполнитель сверяется с DoD. В отчёт добавляет раздел `Lessons:` с 0–3 предложениями уроков. | M |
| KAN-6 | По хукам `kanban_task_completed` и `kanban_task_blocked` прогон записывается автоматически (агент, задача, доска, исход, отчёт). Повторное событие не дублирует запись. | M |
| KAN-7 | На карточке Kanban в Desktop показывается значок: slug агента, уровень, версия SOUL (desktop-SDK, Kanban card badges). | S |
| KAN-8 | Финальная подзадача графа — интеграция: сборка результатов и проверка исходного DoD. | S |

### 2.4 Самосовершенствование (EVO)

| ID | Требование | Пр. |
|---|---|---|
| EVO-1 | Каждый завершённый или заблокированный прогон попадает в очередь ретроспектив. | M |
| EVO-2 | Ретроспектива (§5.4) для каждого прогона: оценка 0..1, сложность, выполнен ли DoD, число циклов доработки, **чья ошибка** — исполнителя или планирования. | M |
| EVO-3 | Урок имеет тип `do / dont / check / context`. Он должен быть конкретным и проверяемым; общие пожелания отклоняются. Дубликаты не сохраняются. | M |
| EVO-4 | Ошибка планирования записывается как урок оркестратору (его память или навык планирования), а не исполнителю. | M |
| EVO-5 | Эволюция переписывает раздел «Lessons learned» в SOUL агента между маркерами. Остальной SOUL не меняется. Версия +1, предыдущая сохраняется. | M |
| EVO-6 | Любая версия SOUL доступна для просмотра, сравнения (diff) и отката из GUI. | M |
| EVO-7 | Вывод из ротации: доля успеха < 0.4 при ≥ 5 прогонах, либо есть агент, стабильно лучший на той же компетенции. Профиль не удаляется. | M |
| EVO-8 | Режим эволюции (`evolve_approval`): `ask` — изменения SOUL показываются как diff и применяются после подтверждения; `auto` — сразу. | M |
| EVO-9 | Повторяющиеся процедурные уроки (≥ 3 на одну тему) переносятся из SOUL в навык профиля агента, чтобы SOUL не разрастался. | S |
| EVO-10 | Запуск ретроспектив: вручную (кнопка в GUI, команда в чате) и по расписанию (встроенный Cron Hermes; задание создаёт пользователь в GUI). | S |

### 2.5 Память (MEM)

| ID | Требование | Пр. |
|---|---|---|
| MEM-1 | Провайдер памяти — Honcho, развёрнутый у пользователя (self-hosted). | M |
| MEM-2 | Эмбеддинги Honcho — локальная модель Google **EmbeddingGemma** (768 измерений) через OpenAI-совместимый эндпоинт (Ollama). | M |
| MEM-3 | Honcho хранит знания о пользователе: предпочтения, стиль, решения, историю. Знания о проекте хранит RAG (§2.6), методику агентов — их SOUL. Дублирования между слоями нет. | M |
| MEM-4 | Выбор провайдера и настройки подключения делаются в GUI: **System → Memory** (dashboard или Desktop). | M |
| MEM-5 | DLC проверяет, что эндпоинт эмбеддингов доступен и возвращает ожидаемую размерность, и показывает результат в GUI (§4.4). | S |

### 2.6 База знаний / RAG (RAG)

| ID | Требование | Пр. |
|---|---|---|
| RAG-1 | Коллекции знаний (по проекту, документации, спецификациям). Добавление файла, папки или текста. | M |
| RAG-2 | Эмбеддинги — тот же локальный эндпоинт, что у Honcho. Для EmbeddingGemma применяются префиксы задач: запрос — `task: search result | query: `, документ — `title: none | text: `. | M |
| RAG-3 | Повторная индексация источника заменяет его фрагменты, а не дублирует их. | M |
| RAG-4 | Служебные каталоги (`.git`, `node_modules`, `venv`, `dist` и т. п.) и бинарные файлы пропускаются. | M |
| RAG-5 | Агент ищет в базе знаний до того, как строить предположения о проекте (правило в протоколе). | M |
| RAG-6 | Управление коллекциями из GUI: список, размер, переиндексация, удаление. Индексация папки — через выбор папки в GUI. | S |
| RAG-7 | При объёме больше ~100 тыс. фрагментов — векторный индекс (sqlite-vec или LanceDB) вместо перебора. | C |
| RAG-8 | Учёт модели эмбеддингов: фрагменты, посчитанные другой моделью, не смешиваются в поиске. При смене модели GUI предлагает переиндексацию. | M |

## 3. Нефункциональные требования

| ID | Требование |
|---|---|
| NFR-1 | **GUI-first.** Повседневная работа (задачи, библиотека, ретроспективы, одобрения, настройки) не требует терминала. |
| NFR-2 | **Без автоматической установки.** Пакет ставится через **Capabilities → Plugins → Install**. Пакет не содержит установочных скриптов и сам не выполняет `docker`, `ollama pull`, `pip install`. Действия, меняющие систему (создание профиля, правка SOUL), выполняются только по явному действию пользователя или по включённому им режиму `auto`. |
| NFR-3 | **Ядро не трогаем.** Только публичный API: `ctx.register_tool / register_hook / register_skill / register_command / register_system_prompt_section`, desktop-SDK, `dashboard/plugin_api.py`. Импорт только модулей из таблицы Public plugin API. |
| NFR-4 | **Обратимость.** Любое изменение агента имеет версию и откатывается из GUI. Выведенный из ротации агент сохраняется. |
| NFR-5 | **Прозрачность.** Каждое решение оркестратора (сложность, рекомендация `reuse/adapt/forge` и её причина, уроки) видно в чате и в GUI библиотеки. |
| NFR-6 | **Локальность.** Эмбеддинги и данные библиотеки — на машине пользователя. Наружу уходят только запросы к LLM-провайдерам, выбранным пользователем. |
| NFR-7 | **Отказоустойчивость.** Недоступность эмбеддера не ломает работу: подбор агента переходит на поиск по ключевым словам с пометкой в GUI. Ошибки хуков не ломают Kanban. |
| NFR-8 | **Бюджет промпта.** Секция DLC в системном промпте ≤ 2000 символов. Методика лежит в навыках, которые загружаются по требованию. |
| NFR-9 | **Без внешних Python-зависимостей** в агентской части (stdlib: sqlite3, urllib). |

## 4. Архитектура

### 4.1 Состав пакета

Один устанавливаемый пакет («unified package») в корне репозитория:

```
hermes-dlc/
├── plugin.yaml              агентская часть: инструменты, хуки, команды, config_schema
├── __init__.py              register(ctx)
├── dlc/                     логика: library, rag, embed, store
├── skills/
│   ├── task-planning/SKILL.md
│   ├── agent-forge/SKILL.md
│   └── retrospective/SKILL.md
├── dashboard/
│   ├── manifest.json        { "name": "dlc", "api": "plugin_api.py" }
│   └── plugin_api.py        REST для GUI: /api/plugins/dlc/...
└── desktop/
    └── plugin.js            страница «Агенты», «Знания», значки Kanban, настройки
```

Установка: Desktop → **Capabilities → Plugins → Install** → URL репозитория → просмотр
коммита → Install. Desktop сам копирует `desktop/plugin.js` в `desktop-plugins/dlc/`.
Включение для других профилей — кнопка **Install here** при выборе профиля в колонке Agent.

### 4.2 Компоненты

```
┌────────────────────────── Hermes Desktop ─────────────────────────────┐
│ Чат (оркестратор)   Kanban (+значки DLC)   Страница «Агенты»  «Знания» │
└──────┬───────────────────────┬────────────────────┬───────────────────┘
       │ tools dlc_*           │ hooks kanban_*     │ ctx.rest
┌──────▼───────────────────────▼────────────────────▼───────────────────┐
│ Агентская часть DLC (plugin.yaml)          dashboard/plugin_api.py    │
│  • протокол в системном промпте            • чтение/правка библиотеки │
│  • навыки dlc:*                            • одобрения, diff, откат   │
│  • library / rag / embed                   • коллекции RAG            │
└──────┬──────────────────────────────┬─────────────────────────────────┘
       │                              │
  ~/.hermes/dlc/dlc.db          Ollama (embeddinggemma)  ◄── Honcho (self-hosted)
  ~/.hermes/dlc/history/        localhost:11434/v1
  ~/.hermes/profiles/ag-*/
```

### 4.3 Модель данных (`~/.hermes/dlc/dlc.db`, SQLite, WAL)

| Таблица | Поля |
|---|---|
| `agents` | slug PK, title, specialty, domains (json), tier, profile, model, status (`proposed/active/retired`), version, parent_slug, embedding (float32 blob), created_at, updated_at |
| `runs` | id, agent_slug, task_id, board, outcome (`completed/blocked/failed/rework`), complexity, score, notes, retro_done, at; UNIQUE(agent_slug, task_id, outcome) |
| `lessons` | id, agent_slug, lesson, kind (`do/dont/check/context`), source_task, applied, at |
| `proposals` | id, type (`forge/evolve/retire/merge`), payload (json), status (`pending/approved/rejected`), created_at, decided_at |
| `chunks` | id, collection, source, ord, text, embedding, model, at |

Файлы: `~/.hermes/dlc/history/<slug>/v<N>.SOUL.md` — все версии SOUL.

### 4.4 GUI (desktop/plugin.js)

**Страница «Агенты»** (пункт в боковой панели):
- Таблица: slug, уровень, компетенция, версия, число прогонов, доля успеха, средняя оценка,
  статус. Фильтры по статусу, уровню, домену; поиск.
- **Входящие одобрения** сверху: предложения `forge / evolve / retire / merge`.
  Для forge — полный SOUL; для evolve — diff SOUL. Кнопки «Одобрить», «Изменить», «Отклонить».
- **Карточка агента**:
  - SOUL: просмотр и правка; правка вручную создаёт новую версию;
  - уроки с удалением и правкой;
  - история прогонов со ссылками на Kanban-задачи;
  - версии SOUL: diff любой пары, кнопка «Откатить»;
  - действия: «Вывести из ротации», «Создать наследника».
- **Очередь ретроспектив**: прогоны без разбора; кнопка «Разобрать» отправляет оркестратору
  в чат команду `/retro`.

**Страница «Знания»**: коллекции (фрагменты, источники, модель), «Добавить папку…» через выбор
папки, «Переиндексировать», «Удалить», поле пробного поиска.

**Kanban**: значок на карточке (`ag-slug · tier · vN`).

**Settings → Plugins → DLC**: форма из `config_schema` (§6) и статус эмбеддера: адрес,
модель, фактическая размерность, кнопка «Проверить».

### 4.5 Инструменты агента

| Инструмент | Назначение |
|---|---|
| `dlc_agent_find` | Подбор по компетенции → кандидаты и `reuse/adapt/forge` |
| `dlc_agent_forge` | Создание специалиста (или предложения при `forge_approval=ask`) |
| `dlc_agent_list` | Библиотека со статистикой |
| `dlc_agent_learn` | Запись урока |
| `dlc_agent_evolve` | Вписать уроки в SOUL (или предложение при `evolve_approval=ask`) |
| `dlc_agent_retire` | Вывод из ротации |
| `dlc_run_record` | Оценка прогона |
| `dlc_retro_pending` | Очередь ретроспектив; закрытие без урока |
| `dlc_rag_ingest` | Индексация в коллекцию |
| `dlc_rag_search` | Семантический поиск; без запроса — список коллекций |

Команды в чате: `/agents` (сводка библиотеки), `/retro` (провести ретроспективы).

### 4.6 Секция системного промпта

Добавляется через `register_system_prompt_section`, не длиннее 2000 символов, два варианта:
- **оркестратор** — протокол: триаж → подбор → Kanban → ретроспектива; RAG до догадок;
  число ожидающих ретроспектив;
- **исполнитель** (задан `HERMES_KANBAN_TASK`) — работать в своей компетенции, чужое блокировать
  с описанием нужной компетенции, сверка с DoD, раздел `Lessons:`.

## 5. Алгоритмы

### 5.1 Триаж сложности

| Уровень | Признаки | Действие |
|---|---|---|
| trivial | 1 шаг, ответ очевиден | Сам, без плана |
| simple | 2–3 шага, одна область, известный паттерн | Сам; Kanban не нужен |
| moderate | Несколько областей или нужна проверка | Kanban, 2–5 подзадач, специалисты по LIB-8 |
| complex | Много областей, зависимости, высокая цена ошибки | Kanban-граф, специалисты, ревью, план на утверждение |
| novel | Нет известного решения | Spike → план → как complex |

Подзадачу больше ~2 часов работы агента или с двумя разными компетенциями режем дальше.

### 5.2 Подбор агента

1. Эмбеддинг запроса `need + домены` (префикс query) сравнивается косинусом с эмбеддингом
   компетенции каждого активного агента (при необходимости с фильтром по уровню).
2. `success_rate = (успехи + 1) / (прогоны + 2)` — сглаживание Лапласа; новый агент = 0.5.
3. `rank = similarity × (0.75 + 0.25 × success_rate)`.
4. Рекомендация по лучшему кандидату:
   - `reuse` — similarity ≥ `reuse_threshold` (0.78) и success_rate ≥ 0.4;
   - `adapt` — similarity ≥ `adapt_threshold` (0.60);
   - иначе `forge`.
5. Без эмбеддера — коэффициент Жаккара по токенам с порогами 0.45 / 0.25; в ответе метод `keyword`.
6. Пороги — начальные. Калибровка обязательна (§9, этап 2).

### 5.3 Шаблон SOUL специалиста

```
# <Роль>
Ты — <кто>. Единственная зона: <компетенция>.

## Зона ответственности
- Делаешь: …
- НЕ делаешь (блокируй с описанием нужной компетенции): …

## Метод
1. С чего начинаешь, что проверяешь первым.
2. Порядок работы, специфичный для области.
3. Как проверяешь результат.

## Стандарты качества
- Конкретные и проверяемые: версии, паттерны, лимиты, стандарты.

## Типичные ошибки области
- Что делает неправильно агент общего профиля → как правильно.

## Definition of Done
- Чек-лист перед kanban_complete.

## Формат сдачи
- Содержимое отчёта, артефакты, раздел Lessons:.

## Lessons learned
<!-- dlc:lessons:start -->
…управляется DLC…
<!-- dlc:lessons:end -->
```

Требования к созданию: `slug` по компетенции (`pg-zero-downtime-migrations`, а не `coder-2`),
одна компетенция на агента, SOUL ≥ 200 символов со всеми разделами.

### 5.4 Ретроспектива

1. Взять прогон из очереди и открыть задачу: постановку, результат, комментарии, ревью, `Lessons:`.
2. Оценить: DoD, циклы доработки, причина блокировки, соответствие задачи компетенции.
3. Записать оценку (`dlc_run_record`).
4. Извлечь 0–3 урока. Ошибку планирования адресовать оркестратору. Внешние сбои
   (упал API, нет доступа) уроками не считаются.
5. Новые уроки есть → эволюция (с одобрением или без, по `evolve_approval`).
6. Проверить условия вывода из ротации (EVO-7) и слияния (LIB-10).

### 5.5 Эволюция SOUL

- Сохранить текущий SOUL как `v<N>`.
- Заменить содержимое между маркерами на последние `max_lessons_in_soul` (25) уроков.
  Устаревшие или противоречивые уроки удаляются явно.
- Маркеров нет — раздел дописывается в конец.
- `version = N + 1`; уроки помечаются как применённые.

## 7. Окружение (готовит пользователь вручную)

DLC его не устанавливает и не настраивает. Здесь описано, что должно быть.

### 7.1 Эмбеддинги
- Ollama (есть GUI-приложение для macOS и Windows) с моделью `embeddinggemma`.
- Эндпоинт `http://localhost:11434/v1/embeddings` возвращает векторы длиной 768.
- Проверка — кнопка «Проверить» в настройках DLC (§4.4).

### 7.2 Honcho (self-hosted)
Сервер Honcho своего GUI не имеет. Запускается через Docker (Docker Desktop: compose-проект
из репозитория `plastic-labs/honcho`). Обязательные параметры его `.env` — пример в
`infra/honcho/.env.example`:

| Параметр | Значение | Зачем |
|---|---|---|
| `EMBEDDING_VECTOR_DIMENSIONS` | `768` | Размерность EmbeddingGemma. **Задаётся до первого запуска**: она фиксируется в схеме pgvector, смена = пересоздание БД. |
| `EMBEDDING_MODEL_CONFIG__TRANSPORT` | `openai` | OpenAI-совместимый протокол Ollama |
| `EMBEDDING_MODEL_CONFIG__MODEL` | `embeddinggemma` | |
| `EMBEDDING_MODEL_CONFIG__OVERRIDES__BASE_URL` | `http://host.docker.internal:11434/v1` | Ollama на хосте из контейнера. На Linux дополнительно нужен `extra_hosts: host-gateway` (`infra/honcho/docker-compose.override.yml`). |
| `EMBEDDING_MODEL_CONFIG__DIMENSIONS_MODE` | `never` | Не отправлять `dimensions=` |
| LLM для deriver, summary, dialectic, dream | Gemini Flash/Pro или локальная модель с tool calling | Без LLM Honcho не стартует |

Подключение к Hermes — в GUI: **System → Memory** (веб-дашборд Hermes) → провайдер Honcho → адрес
`http://127.0.0.1:8000`. Параметры хоста `hermes`: `recallMode: hybrid`, `writeFrequency: async`,
`sessionStrategy: per-directory`.

### 7.3 Kanban
Доска создаётся в Desktop на странице Kanban. Gateway (на нём работает диспетчер) запускается в
**System → Gateway** (веб-дашборд Hermes).

## 8. Критерии приёмки v1

1. Пакет ставится через **Capabilities → Plugins → Install** без терминала. В колонке Agent
   он включён, страница «Агенты» появилась.
2. Задача «добавь в FastAPI-проект OAuth2 PKCE и миграцию пользователей в PostgreSQL без простоя»:
   - оркестратор выдаёт цель, DoD, оценку `complex`, план из 3+ подзадач по компетенциям;
   - на каждую подзадачу вызывается `dlc_agent_find`;
   - при пустой библиотеке в GUI появляются предложения `forge` с полным SOUL;
   - после одобрения создаются профили `ag-*`, на Kanban появляются связанные задачи.
3. Исполнители завершают задачи, прогоны записаны, значки на карточках видны.
4. `/retro`: уроки записаны, в GUI появилось предложение `evolve` с diff. После одобрения
   версия SOUL = 2, откат на v1 из GUI работает.
5. Повторная похожая задача → `dlc_agent_find` возвращает `reuse` для созданных агентов.
6. Задача `simple` выполняется без Kanban и без создания агентов.
7. Ollama выключена → подбор работает с методом `keyword`, GUI показывает предупреждение,
   Kanban не ломается.
8. Honcho: после 10+ сообщений его поиск находит факты о пользователе.
   В настройках DLC видна размерность эмбеддера 768.

## 10. Риски и открытые вопросы

| # | Вопрос | Предлагаемое решение |
|---|---|---|
| R1 | Разрастание библиотеки мелкими агентами | LIB-8, LIB-10, одобрение forge по умолчанию |
| R2 | Шум в уроках, раздувание SOUL | EVO-3, лимит 25, перенос в навыки (EVO-9), одобрение evolve |
| R3 | Каждый профиль агента требует ключи провайдера | Профили клонируются с ключами активного профиля (`--clone`); на агента не нужен отдельный gateway |
| R4 | Пороги подбора не откалиброваны | Этап 3; пороги в настройках |
| R5 | Смена модели эмбеддингов ломает Honcho | MEM: размерность фиксирована; смена = пересоздание БД Honcho, вынесено в предупреждение GUI |
| R6 | Профиль агента не получил плагин DLC → хуки не пишут прогоны | При создании профиля DLC проверяет, что плагин включён; в карточке агента — индикатор «DLC активен» |
| Q1 | Нужны ли разные доски Kanban под проекты? | Встроенные доски Hermes; DLC их не различает, `board` пишется в прогон |
| Q2 | Модели по уровням: конкретные значения | Задаёт пользователь в настройках |
