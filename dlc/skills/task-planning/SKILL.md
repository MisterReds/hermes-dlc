# Планирование задачи

Цель: не начинать работу, пока задача не понята и не разложена на части, каждой из которых
назначен исполнитель с подходящей компетенцией. Ошибка планирования стоит дороже любой ошибки
исполнения.

## When to Use
- Любая задача, где больше одного шага, больше одного артефакта или неочевидный критерий готовности.
- Не использовать для тривиальных вопросов и однострочных правок.

## Procedure

### 1. Понимание (обязательно, до всего остального)
Сформулируй письменно:
- **Цель** — какой результат нужен пользователю, а не что он буквально сказал.
- **Артефакты** — что конкретно должно существовать в конце (файлы, PR, документ, деплой).
- **Критерий готовности (DoD)** — как проверить, что сделано. Проверяемо, без "хорошо/красиво".
- **Ограничения** — стек, сроки, стиль, что трогать нельзя.
- **Неизвестные** — что неясно. Если неизвестное меняет план — спроси пользователя (`clarify`)
  ДО декомпозиции. Если не меняет — зафиксируй допущение.
- Проверь контекст: `dlc_rag_search` по проекту, память (Honcho) о предпочтениях пользователя.

### 2. Триаж сложности
| Уровень | Признаки | Действие |
|---|---|---|
| trivial | 1 шаг, ответ очевиден | Сделай сам, без плана |
| simple | 2–3 шага, одна область, известный паттерн | Сделай сам или 1 задача на generalist |
| moderate | несколько областей ИЛИ нужна проверка | Kanban, 2–5 подзадач, специалисты где нужно |
| complex | много областей, зависимости, риск ошибки | Kanban-граф, специалисты, обязательный review |
| novel | нет известного решения, исследование | Сначала задача-исследование (spike), потом план |

Сложность определяется **самой трудной подзадачей**, а не средней.

### 3. Декомпозиция
- Режь по **компетенции и артефакту**, а не по ролям "кодер/ревьюер/дизайнер".
  Плохо: "кодер пишет бэкенд". Хорошо: "миграция схемы PostgreSQL с zero-downtime",
  "OAuth2 PKCE flow для мобильного клиента", "вёрстка формы по макету с a11y AA".
- Каждая подзадача: один исполнитель, один проверяемый результат, явные входы (от каких
  родителей зависит) и DoD.
- Подзадача > ~2 часов работы агента или с двумя разными компетенциями — режь дальше.
- Явно отметь, где нужен review и **какой компетенции** ревьюер (ревьюер тоже специалист).

### 4. Подбор исполнителей
Для каждой подзадачи определи **требуемую компетенцию** (не текст задачи) и вызови
`dlc_agent_find(need=..., domains=[...], tier=...)`:
- `reuse` → назначь профиль кандидата.
- `adapt` → близкий агент есть, но задача уже его специализации: создай узкого наследника
  через `dlc_agent_forge` с `parent_slug`.
- `forge` → создай специалиста (скилл `dlc:agent-forge`).
- Для `simple`-подзадач generalist допустим — не плоди специалистов без необходимости.
  Критерий: если generalist с вероятностью >20% сделает неверно или неидиоматично — нужен специалист.
- tier: simple → дешёвая модель; specialist → основная; expert → сильная модель.

### 5. Раскладка на Kanban
- `kanban_create` для каждой подзадачи: `assignee` = профиль агента, в теле — цель, входы,
  DoD, ограничения, ссылки на нужные RAG-коллекции. Связи — через `parents`.
- Задачи без зависимостей идут параллельно.
- Финальная задача-интеграция: сборка результатов + проверка общего DoD.

### 6. Зафиксируй план
Короткий план пользователю: уровень сложности, подзадачи, исполнители (reuse/forge), риски.
Для complex/novel — дождись подтверждения, если пользователь не сказал действовать сам.

## Pitfalls
- Начать делать до формулировки DoD.
- Декомпозиция по должностям вместо компетенций.
- Специалист "fullstack-разработчик" — это не специалист.
- Пропуск `dlc_agent_find`: библиотека не растёт и не учится.
- Ревьюер без нужной компетенции пропустит ровно те ошибки, которые важны.

## Verification
- У каждой подзадачи есть исполнитель, DoD и входы.
- Ни один исполнитель не получил задачу вне своей специализации (кроме simple).
- План покрывает исходный DoD целиком.
